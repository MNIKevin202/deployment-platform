# Blueprint

Blueprint is the platform's first-party private AI workspace: a chat
interface running on the operator's own VPS, backed by a model server that
is never exposed to the internet. It is installed from **One-click
templates → AI → Blueprint**.

It is also the first *multi-service* template, and the companion mechanism
it introduced (below) is generic — future templates such as Immich,
Paperless-ngx, or a monitoring stack can reuse it without new plumbing.

## What gets deployed

Installing Blueprint creates **two ordinary managed apps**:

| App | Image | Routing | Storage |
| --- | --- | --- | --- |
| `blueprint` | `ghcr.io/open-webui/open-webui:0.11.0` | Public HTTPS domain | `/app/backend/data` |
| `blueprint-ollama` | `ollama/ollama:0.32.5` | **Internal only** — no domain, no published port | `/root/.ollama` |

Both names follow whatever app name the operator chooses, so a second
install (`studio-ai`) produces `studio-ai` and `studio-ai-ollama` with no
collision.

The chat interface reaches the model server over the platform's private
`deployment-apps` Docker network by container name:

```
OLLAMA_BASE_URL = http://app-blueprint-ollama:11434
```

Never `localhost`, never the VPS public IP. The model server has no Caddy
route and no published host port, so it is unreachable from the internet.

### Environment

| Variable | Value | Notes |
| --- | --- | --- |
| `OLLAMA_BASE_URL` | `http://app-<name>-ollama:11434` | Resolved from the template's `{{companion:ollama}}` placeholder at install time |
| `WEBUI_SECRET_KEY` | generated, 48 chars, secret | **Required** — Open WebUI 0.11 refuses to start with auth enabled and no key. Generated by the platform's existing `generateSecret`; never hardcoded, never logged |
| `ENABLE_OPENAI_API` | `false` | V1 is local-models-only. No cloud provider credentials are requested |

The first account created in the web interface becomes its administrator —
Open WebUI has no secure way to seed an admin from environment variables,
so V1 deliberately does not try.

## The companion mechanism (generic)

A template may declare `companions` (see `apps/web/src/lib/appTemplates.ts`):

```ts
companions: [{
  key: "ollama",          // referenced by {{companion:ollama}}
  nameSuffix: "-ollama",  // blueprint -> blueprint-ollama
  label, description,
  image, containerPort,
  internalOnly: true,     // default
  volumes: ["/root/.ollama"]
}]
```

Each companion is created as a **normal managed app** through the very same
`createAppWithConfig()` the wizard already used — there is no parallel
deployment system. Consequences, all inherited rather than reimplemented:

- companions appear on the Apps page and can be inspected, redeployed, and
  deleted individually;
- routing, volumes, health checks, metrics, image-update checks, backups,
  and deletion cleanup all apply unchanged;
- a companion cannot publish a host port at all — the schema has no field
  for it, so a template can never quietly open one for a backing service.

`deployTemplateStack` (`apps/api/src/services/template-deployment-service.ts`)
adds only ordering and failure handling:

1. companions are created **first**, so the main app can reach them on its
   first boot instead of crash-looping;
2. if anything fails — a companion, the main app, or a thrown Docker error —
   everything the call already created is removed again, in reverse order.
   A rollback that itself fails is reported by name in the error message
   rather than hidden.

Idempotency keys are derived per companion (`<key>:companion:<name>`) so a
transport-level retry replays the whole stack instead of re-creating
companions under an already-taken name.

## Models

No model is downloaded automatically without a choice. The template detail
view offers a curated, CPU-friendly list, defaulting to the balanced option:

| Model | Size | Notes |
| --- | --- | --- |
| `llama3.2:1b` | ~1.3 GB | Fastest; best on a 4 GB server |
| `qwen3:1.7b` | ~1.4 GB | |
| `llama3.2:3b` | ~2.0 GB | **Default.** Good on 8 GB |
| `gemma3:4b` | ~3.3 GB | |
| `llama3.1:8b` | ~4.9 GB | Needs 8 GB+; noticeably slower on CPU |

Every identifier was verified against `registry.ollama.ai` rather than
assumed. "Don't download a model now" is always available.

The download runs as a **post-deployment task**, not part of the deploy:

- it starts only after the app exists and is running;
- a failed or refused download never fails the app — the install still
  succeeds and the UI explains how to retry;
- progress is tracked per app and streamed into the API log
  (`[blueprint] pull <model>: <status>`);
- only one download runs per app at a time; a second request is refused
  with 409 rather than starting a duplicate;
- a finished download — succeeded or failed — never blocks a retry.

Pull state is in-memory by design (like the image-update cache): after an
API restart the truthful answer is "no download is running", and the
durable fact — which models exist — always comes from Ollama itself.

Model names are validated twice (route schema and service) against a strict
charset, rejecting whitespace, quotes, shell metacharacters, URLs, and `..`
traversal outright rather than escaping them.

## API

All routes are keyed by the **Blueprint app's** id; the model server is
never addressed directly from the browser, and its container name is
resolved server-side from the app's own `OLLAMA_BASE_URL`.

| Route | Purpose |
| --- | --- |
| `GET /apps/:id/blueprint/status` | Both service states, version, installed models, storage used, current pull |
| `GET /apps/:id/blueprint/pull` | Current pull state only |
| `POST /apps/:id/blueprint/models` | Start a download (`{ model }`), rate-limited |
| `DELETE /apps/:id/blueprint/models` | Delete a model (`{ model }`), rate-limited |

## Deleting

Deleting either app follows the platform's existing rules: the container is
removed, the app record and its routing are cleaned up, and **named volumes
are preserved** — exactly as for every other app here. Deleting `blueprint`
does not delete `blueprint-ollama`; both are deleted individually, and
downloaded models survive an app update or redeploy rather than being
silently discarded.

## Known limitations (V1)

- **CPU only.** No GPU configuration of any kind; responses generate
  gradually on small servers. The template says so before install, in the
  wizard, and permanently on the Blueprint tab.
- **No cloud providers.** No OpenAI/Anthropic/Gemini keys are requested.
- **No admin seeding.** The first account created becomes admin.
- **Volumes outlive the app** (platform-wide behaviour). Downloaded models
  keep occupying disk after a delete until the volume is removed.
- **Pull state resets on API restart.** A download in flight when the API
  restarts continues inside Ollama, but the panel shows no progress bar for
  it; the model appears in the list when it completes.
- **Host disk is not pre-checked.** RAM and vCPU are compared against the
  template's stated minimum before install; free disk space is not, since
  the platform has no host-disk figure at that point.

## Open WebUI features that must stay off

Open WebUI 0.11 enables **Notes, Calendar, Automations, and the code
interpreter** by default. Each registers a *native tool* that is attached to
every chat message, and that breaks Blueprint on the small CPU models this
template is built around. Verified live on a 2 vCPU server:

- **Gemma models reject the request outright** — Ollama answers
  `registry.ollama.ai/library/gemma3:4b does not support tools` and nothing
  is generated at all.
- **Llama 3.2 accepts tools**, and a 1–3B model handed a pile of function
  schemas stops replying and starts emitting invented calendar/note code.
  A plain "hello" came back as a page of Google Calendar Python. The same
  model answers "hello" correctly the moment the tools are removed.

An empty `tools: []` array is fine — only a non-empty one triggers this, so
it is the built-in features, not the per-chat tool picker, that cause it.
Turning tools off in the chat UI does **not** help.

The template therefore ships with `ENABLE_CALENDAR`, `ENABLE_NOTES`,
`ENABLE_AUTOMATIONS`, and `ENABLE_CODE_INTERPRETER` set to `false`, plus
`ENABLE_FOLLOW_UP_GENERATION=false` (a second model call per message, on a
box where CPU is the scarce resource). Re-enable any of them from Admin
Settings once a tool-capable model is in use.

**Existing installs** predate this and still have the features on. Fix an
existing Blueprint app by adding those environment variables from its
Environment tab and redeploying, or by switching the features off in
Open WebUI's Admin Settings.

## Measured performance (2 vCPU, 7 GB VPS)

| Model | Speed | Notes |
| --- | --- | --- |
| `gemma3:270m` | ~37 tok/s | ~3.5x faster than the 1B; short chat only |
| `llama3.2:1b` | ~11–17 tok/s | Derails on longer prompts |
| `gemma3:4b` | ~12 tok/s | Coherent; a good default at this size |

Speed is rarely the real complaint — an incoherent model that will not stop
generating feels far slower than a coherent one at the same tokens/second.
